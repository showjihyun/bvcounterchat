## 0. 이 문서가 정하는 것과 정하지 않는 것

`requirements.md` §6(RQ-50~55)은 **무엇을 어디에**만 정한다 — 원본
`docs/req/05_UI_UX.md`가 위치 다섯 개("좌상단 MiniMap / 우상단 Top Scorer /
좌하단 Global Chat / 우하단 HP·Ammo·Kill / 중앙 Crosshair")뿐이기 때문이다.
**어떻게 보이는가**가 비어 있었고 이 문서가 그것을 채운다.

**정하지 않는 것**(다른 문서 소유):
- 요소의 **존재·위치·동작** — `requirements.md` RQ-50~55
- 성능 규칙(인스턴싱·링버퍼·렌더 루프 할당 금지) — `harness/workflow/fe.md`, ADR-0001
- 무엇이 서버 권위인가 — RQ-61/62. **HUD는 판정 결과(HP·킬·명중·헤드샷)를 계산하지
  않는다 — 서버가 보낸 값을 표시한다.** 예측 표시(크로스헤어 확산 §3.1, 미니맵 자기
  위치 §3.5)는 **RQ-62 예측값을 쓰되 서버 값과 어긋나면 서버가 이긴다.**
  ⚠️ 초안은 이 줄을 "HUD는 서버 값을 표시할 뿐 계산하지 않는다"는 절대문으로 적어
  **같은 문서의 §3.1·§3.5를 스스로 금지했다**(1차 리뷰 major). 그대로 두면 다음
  라운드가 그 문면을 근거로 예측 표시를 서버 값 대기로 바꿔 조준이 RTT만큼 밀린다.

## 1. 방향

**기능 우선 · 고대비.** 반투명 어두운 배경 위에 밝은 단색 텍스트.

**왜 이 방향인가**(사용자 결정 2026-08-05):
- 맵이 RQ-30에 따라 **사암색**(`#c2b49a` 하늘 / `#8a7a5c` 바닥 — §2.1)이다. HUD를 같은
  색역으로 맞추면 분위기는 좋으나 **시인성이 떨어지고 저HP 경고 같은 상태
  구분이 어려워진다** — 그래서 "맵과 톤 통일" 안은 기각됐다.
- 어두운 반투명 배경은 **밝은 사암색 하늘·짙은 사암색 바닥 어느 쪽 위에서도** 대비를
  확보한다 — **맵 전체가 한 색역이라 밝기로 가르는 편이 안전하다.**
  ⚠️ 초안은 이 줄을 “사암색·하늘색 어느 쪽 위에서도”라고 적었다(2차 리뷰 minor) —
  바닥을 `#c2b49a`로 잘못 안 상태에서 “그럼 하늘은 파랗겠지”로 쓴 문장이고, 이 게임에
  하늘색(sky blue) 영역은 없다. **§2.1 오기의 마지막 조각이다.**
- 명도 대비를 우선하면 **접근성이 자연히 따라온다** — 색만으로 정보를 전달하지
  않는다는 규칙(§4)을 지키기도 쉽다.

좌표는 `PRODUCTION_GEOMETRY` 한 곳에서만 오고 렌더는 환산만 한다(ADR-0010).

세 색은 바닥(`SCENE.ground`)과 **명도로 갈라** 골랐다 — 벽은 밝게, 박스는 어둡게,

막는 자리가 정확히 여기였다. ⚠️ 벽 **높이**(`SCENE.wallRenderHeightM`, 4m)는 색이
아니라 렌더 선택값이고 **스펙에 근거가 없다**(RQ-30은 플레이 면적만 규정).
**이 값은 이미 부족하다** — 사다리 꼭대기 시점은 4 + 1.7(눈높이) = **5.7m**라 그려진
벽 윗면보다 위이고, 벽 너머가 보이는데 그쪽으로 쏜 탄은 판정상 무한 높이인 기둥에
막힌다. 처분은 원장 **24g**가 갖는다.

⚠️ **초안은 이 표를 두 행 틀리게 적었다**(1차 리뷰 blocker) — 하늘색을 바닥색이라
쓰고, **렌더되지도 않는 벽·박스·사다리에 색을 배정**했다. 원인은 씬 색에 **코드
정본이 없어서** 문서만 값을 갖게 된 것이다(원장 24c). 이 문서가 같은 PR에서
"정본은 코드, 표는 미러"를 선언해 놓고 그 코드를 잘못 읽었다.

**원장 26r과의 관계 — 부분만 닫힌다.** 26r은 RQ-30의 "사암색 팔레트, 건조한
지중해풍"이 자동 검증 불가라 디자인 리뷰의 몫인데 그 문서가 없다고 적었다. 이 표는
**현재 렌더되는 것**(하늘·바닥·플레이어)의 팔레트를 기록해 그 판단 근거를 만든다.
**맵 지오메트리 색은 원장 24f에서 정해져 이 표에 들어왔다** —
26r은 그때 완전히 닫힌다.

### 2.2 타이포

| 토큰 | 값 | 쓰임 |
|---|---|---|
| `--font` | `system-ui, -apple-system, 'Segoe UI', sans-serif` | 전역(기존) |
| `--size-sm` | `0.8rem` | 채팅 로그·킬 피드·보조 |
| `--size-md` | `0.85rem` | 입력창·본문 |
| `--size-lg` | `1.5rem` | HP·탄약 수치, 입장 화면 제목 |
| `--weight-strong` | `600` | 닉네임·수치 |

**2단계 + 강조 하나**로 끝낸다. 게임 HUD는 읽는 문서가 아니라 **곁눈질로 확인하는
계기판**이라 위계가 얕을수록 낫다.

### 2.3 간격

**4px 배수 스케일.** 기존 CSS가 이미 `0.25rem`(4px)·`0.5rem`(8px)·`1rem`(16px)을
쓰고 있어 그것을 규칙으로 승격한다.

| 토큰 | 값 |
|---|---|
| `--space-1` | `0.25rem` (4px) |
| `--space-2` | `0.5rem` (8px) |
| `--space-3` | `1rem` (16px) |
| `--space-4` | `1.5rem` (24px) |
| `--radius` | `4px` |

**화면 가장자리 여백은 `--space-3`(16px)로 통일한다** — 기존 `bottom: 1rem;
left: 1rem`이 이미 그 값이다.

⚠️ **컴포넌트 치수는 이 스케일이 아니다.** 채팅 패널 너비(`22rem`)·로그 최대
높이(`8rem`)·입장 폼 너비(`16rem`)는 "그 내용이 읽히는 크기"에서 온 값이라
4px 배수를 따르지 않는다 — 스케일은 **여백과 안쪽 여백**에만 적용한다. 그
구분을 두지 않으면 모든 치수를 스케일에 맞추려다 내용이 잘린다.

## 3. 요소별 스펙 (RQ-50~55)

모든 HUD 요소는 `.hud`(`pointer-events: none`) 안에 있다. **입력을 받는 요소만
개별적으로 `pointer-events: auto`를 되살린다** — 조준·사격이 캔버스로 가야 한다.

### 3.1 크로스헤어 (RQ-54, 중앙)

**형태**: 중앙 간격을 둔 십자 4선(원장 24e에서 22b의 임시 점을 교체했다) —
선이라야 **탄퍼짐 확장을 표현할 수 있다**.

| 속성 | 값 |
|---|---|
| 선 길이 | 6px |
| 선 굵기 | 2px |
| 색 | `--fg-strong` + `--shadow-text` |
| 기본 간격(중심↔선 안쪽) | 4px |

✅ **원장 24e에서 정식 십자로 교체됐다** — 22b의 임시 점과 그 지름 상수
`CROSSHAIR.dotPx`는 **제거됐다**. 구현은 `src/client/hud/Crosshair.tsx`(4선)와
`@client/hud/crosshairSpread`(간격 계산)다.

⚠️ 24a 1차 리뷰 major가 잡은 사고가 이 자리였다 — 토큰화하면서 선 굵기(2px)를
임시 점의 지름(4px)에 물려 **조준점이 절반이 됐다**. 굵기와 지름은 **다른 양**이고,
자동 게이트가 전량 초록인 채 통과했다(ADR-0008 §6 — 렌더 계층에는 그물이 없다).

**탄퍼짐 확장** — RQ-90의 3단계와 **같은 배율을 쓴다**(새 수치를 만들지 않는다):

| 상태 | 콘 배율 | 간격 |
|---|---|---|
| 정지·앉기 | ×1 | 4px |
| 이동 | ×2 | 8px |
| 공중 | ×4 | 16px |

즉 **간격 = 기본 간격 × 콘 배율**이다. 배율의 정본은
`src/shared/config/combat-tuning.ts`의 `DEFAULT_SPREAD`이고 HUD는 그것을 읽는다 —
**값을 복제하지 않는다**(ADR-0010).

⚠️ **크로스헤어는 예측 표시다.** 실제 편차는 서버가 시드로 정하고(RQ-90/22v)
클라는 그 시드를 알 수 없다 — **간격은 "이만큼 퍼질 수 있다"는 안내이지
탄착점이 아니다.** 이 구분을 코드 주석에도 남긴다.

### 3.2 HP · 탄약 · 킬 (RQ-53, 우하단)

한 줄 배치: `HP  100   ┃   10 / 10   ┃   K 3`

| 요소 | 크기 | 색 |
|---|---|---|
| HP 수치 | `--size-lg` / `--weight-strong` | `--fg-strong`, **HP ≤ 25면 `--danger`** |
| 탄약 `현재/탄창` | `--size-lg` / `--weight-strong` | `--fg-strong`, **현재 0이면 `--danger`** |
| 킬 수 | `--size-md` | `--fg` |
| 라벨(HP·K) | `--size-sm` | `--fg-muted` |

**저HP 임계 25는 유도값이다** — `WEAPON.DAMAGE_BODY`(25)에서 왔다. 즉 **"바디
한 발 더 맞으면 죽는다"**가 경고의 뜻이고, 임의의 백분율이 아니다.

⚠️ **색만으로 알리지 않는다** — 저HP·탄약 0에서 수치 옆에 점(`•`)을 함께 띄운다.

### 3.3 채팅 (RQ-52, 좌하단)

기존 구현을 토큰으로 옮기는 수준이고 구조는 유지한다.

| 속성 | 값 |
|---|---|
| 너비 | `22rem`, `max-width: calc(100vw - var(--edge-inset) * 2)` |
| 로그 최대 높이 | `8rem`, 넘치면 스크롤 |
| 로그 배경 | `--panel`, `--radius` |
| 입력창 배경·테두리 | `--panel-strong` / `--border` |
| 닉네임 | `--weight-strong` |

**입력창만 `pointer-events: auto`.** 포커스 중 게임 입력 차단은 이미 구현돼
있다(원장 23a — 최상단 게이트, 개별 핸들러 분산 체크 금지).

### 3.4 킬 피드 (RQ-55, 우상단 아래)

RQ-55가 **5초 노출 · 최대 5줄**을 이미 정했다. 시각만 정한다.

| 속성 | 값 |
|---|---|
| 행 형식 | `가해자 → 피해자` |
| 크기 | `--size-sm` |
| 배경 | `--panel`, 행마다 `--radius` |
| 행 간격 | `--space-1` |
| 자신이 관여한 행 | 닉네임에 `--accent` |
| **헤드샷 구분** | 화살표를 `→`에서 **`⇒`**로 바꾸고 `--danger` 적용 |

⚠️ **헤드샷 구분도 색만으로 하지 않는다** — 화살표 모양이 함께 바뀐다. RQ-55가
"구분 가능하게"만 요구하고 수단은 정하지 않았다. `headshot` 플래그는 서버가
보낸다(ADR-0005) — **클라가 판정하지 않는다**.

### 3.5 미니맵 (RQ-50, 좌상단)

| 속성 | 값 |
|---|---|
| 크기 | 160 × 160px |
| 축척 | **맵 60m → 160px = 2.67px/m** (`WORLD.SIZE_M`에서 유도) |
| 배경 | `--panel`, `--radius` |
| 테두리 | `--border` |
| 자기 표시 | `--accent` 삼각형, **꼭짓점이 바라보는 방향** |
| 세이프존 | `--border` 원, 반경 `WORLD.SAFE_ZONE_RADIUS_M`(4m) × 축척 ≈ 11px |

**타인은 표시하지 않는다.** RQ-50 문면이 "자신의 위치와 방향"만 요구하고,
타인 위치는 **전술 정보라 스펙에 없는 기능을 만드는 것**이 된다(CLAUDE.md 금지 1항).

**구분 기준**(1차 리뷰 minor — 초안의 배제 논거가 세이프존 원을 걸러내지 못했다):
**정적 맵 정보**(세이프존 경계 — 플레이하면 알게 되고 시간에 따라 변하지 않는다)는
"미니맵"이라는 요구의 일부로 본다. **동적 전술 정보**(타인 위치·체력·무기)는 아니다.
맵 지오메트리(벽·박스·사다리)를 그리는 것도 정적 정보라 이 기준상 허용이다 —
그 렌더 메시는 원장 24f에서 씬에 들어왔다(§2.1). 다만 **미니맵에 그것을 투영하는
것**은 아직 하지 않았다.

### 3.6 상위 스코어러 (RQ-51, 우상단)

| 속성 | 값 |
|---|---|
| 표시 | 상위 3명, `순위 닉네임 킬수` |
| 크기 | `--size-sm` |
| 배경 | `--panel`, `--radius` |
| 자신 | `--accent` |

**"상위 3명"은 이 문서의 결정이다** — RQ-51은 "상위 스코어러"라고만 적고 인원을
정하지 않았다. 정원이 10명(RQ-03)이라 3명이면 상위 30%다. ⚠️ 이 수가 스펙 값이
되어야 한다고 판단되면 **RQ-51 개정이 먼저다**(이 문서는 스펙을 못 바꾼다).

## 4. 상태

| 상태 | 표현 | 근거 |
|---|---|---|
| **세이프존 안** | 크로스헤어를 `--fg-muted`로 낮추고 탄약 수치 옆에 `⃠` | RQ-31이 사격을 막는데 **클라가 그것을 모른다**(원장 25t) |
| **재장전 중** | 탄약 자리에 진행 막대(2초, `--accent`) | `WEAPON.RELOAD_MS` = 2000 |
| **사망·리스폰 대기** | 화면 가장자리 `--danger` 비네트 + 중앙 카운트다운 | `PLAYER.RESPAWN_MS` = 3000 |
| **스폰 보호 중** | 자기 표시 주위 `--accent` 링 | **서버 플래그**(아래) |
| **저HP** | §3.2 | `DAMAGE_BODY` = 25 |

**고정 길이 상태(재장전·리스폰)만 게임 상수에서 온다 — 애니메이션 길이를 따로
정하지 않는다.**

⚠️ **조기 해제가 가능한 상태는 클라 타이머로 그리지 않는다**(1차 리뷰 major):

- **스폰 보호** — RQ-16이 "보호 중인 플레이어가 **사격하면 즉시 보호를 해제**"를
  요구한다. 클라가 `SPAWN_PROTECTION_MS`(3000) 타이머로 링을 그리면 **사격으로
  이미 풀린 뒤에도 링이 남아 HUD가 서버와 다른 것을 말한다**. 서버가 보호 플래그를
  스냅샷에 실어야 한다 — 현재 `Player` 스키마에 **없으므로**(`nickname·x/y/z·
  vx/vy/vz·grounded·lastProcessedInputSeq·hp·kills`가 전부) 필드 추가는 그 표시를
  구현하는 라운드의 일이다.
- **세이프존 안** — 사격을 거부하는 주체가 서버이므로(RQ-31) 표시의 정본도 서버다.
  클라가 `@shared/sim/spawn` + 예측 위치로 **선표시**하는 것은 허용하되 서버 값이
  오면 서버가 이긴다. 이 플래그도 현재 스키마에 없다.

§3.4가 헤드샷에 대해 적은 원칙("`headshot` 플래그는 **서버가 보낸다** — 클라가
판정하지 않는다")이 이 두 상태에도 그대로 적용된다.

⚠️ **이 두 플래그를 실제로 배선하는 라운드는 와이어 요구를 RQ 문면에 넣는다** —
RQ-55가 "서버의 킬 이벤트 페이로드가 `headshot` 플래그를 포함해야 한다"로 처리한
선례를 따른다. **이 문서는 서열 4번이라 와이어 계약의 최종 귀속처가 아니다** — 이
문서만 보고 스키마에 필드를 더하면 **스펙 근거 없는 와이어 변경**이 되고 CI의
스펙-코드 동행 경고가 그 자리에서 운다(2차 리뷰 minor).

## 5. 접근성
